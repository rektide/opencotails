# opencode v2: impact on cotails

Research source: `~/archive/anomalyco/v2` (the v2 branch, DISTINCT from `~/archive/anomalyco/opencode` which is v1/main). All `file:line` refs are relative to the v2 checkout root. v2 lives in `packages/{core,cli,server,protocol,schema,...}`; `packages/opencode` is the v1 implementation kept for reference only (`AGENTS.md:4`).

## TL;DR

- **NO — v2 has no CLI transcript-dump command.** The v2 CLI (`packages/cli`) exposes only `api, debug, console, auth, mcp, plugin, migrate(stub), mini, run, service, pair, serve` (`packages/cli/src/commands/commands.ts:36-235`, handler registry at `packages/cli/src/index.ts:16-51`). The v1 `opencode export [sessionID]` command still exists at `packages/opencode/src/cli/cmd/export.ts:222-238` but is v1-only and not wired into the v2 CLI.
- **YES — v2 has a TUI-only "Copy/Export session transcript" action** (interactive, writes to a temp file in `os.tmpdir()`). Markdown renderer = `formatSessionTranscript` at `packages/tui/src/routes/session/index.tsx:3034-3057`. This is the de-facto canonical rendered format and cotails should match it.
- v2 is **event-sourced**: durable events in `event(aggregate_id, seq, ...)` are projected into read tables. The canonical message store is the new `session_message` table, NOT the legacy `message`/`part` tables cotails reads today.
- **Critical migration hazard:** v2 emits only ONE v1 event (`SessionV1.Event.Created`, `packages/core/src/session.ts:374`). It does NOT emit `MessageUpdated`/`PartUpdated`. So a v2-native session creates a row in `session` but leaves `message`/`part` EMPTY. cotails today would show the session with no content.
- Stable message ordinal = `session_message.seq` (= `event.durable.seq`), per-session unique, indexed for both seq-order and date-order range queries.

## Does v2 already dump transcripts?

**No CLI subcommand exists.** The full v2 command spec (`packages/cli/src/commands/commands.ts:17-235`) and its handler registry (`packages/cli/src/index.ts:16-51`) contain no `transcript`, `dump`, `export`, `render`, `share`, or `replay` subcommand. `migrate` is a stub that logs "No migrations to run." (`packages/cli/src/commands/handlers/migrate.ts:5`).

**TUI-only export exists** in `packages/tui/src/routes/session/index.tsx`:
- `session.copy` action — "Copy session transcript": calls `formatSessionTranscript(sessionData, messages(), showThinking())` and writes to clipboard (`packages/tui/src/routes/session/index.tsx:710-728`).
- `session.export` action — "Export session transcript": shows `DialogExportOptions` (format = markdown | json; markdown → include thinking; json → debug events flag), then either copies or writes to `path.join(tmpdir(), "session-<uuid>.{md,json}")` (`packages/tui/src/routes/session/index.tsx:730-799`; options dialog at `packages/tui/src/ui/dialog-export-options.tsx`). Output is always to a random temp path — there is no `--out` flag and no stdout mode.

**v1 export (for reference only):** `packages/opencode/src/cli/cmd/export.ts:222-292` implements `opencode export [sessionID]` with a `--sanitize` flag (`packages/opencode/src/cli/cmd/export.ts:231-234`). It writes `{ info, messages }` JSON to stdout (`packages/opencode/src/cli/cmd/export.ts:287-290`), where `messages` is the v1 `{info, parts}` shape. This is the command cotails is effectively replacing/extending, but it is not exposed by the v2 CLI.

**HTTP endpoints that could serve a dump:** `session.messages` (paginated `SessionMessage.Info[]` via cursor, `packages/server/src/handlers/message.ts:27-80`) and `session.log` (streaming `SessionEvent` via `session.log({after, follow})`, `packages/server/src/handlers/session.ts:647-655`). Neither emits a pre-rendered transcript.

## opencode transcript format

**Canonical rendered format** = `formatSessionTranscript` (`packages/tui/src/routes/session/index.tsx:3034-3057`). Markdown, single document, headers per message. Roles rendered: `user`, `shell`, `assistant`. All other `SessionMessage.Info` types (`system`, `synthetic`, `skill`, `agent-switched`, `model-switched`, `compaction`) are **skipped**. Assistant content items: `text`, `reasoning` (only if `thinking` flag set), `tool`.

Concrete example (reconstructed from `packages/tui/src/routes/session/index.tsx:3034-3057`):

```markdown
# Fix the login bug

**Session ID:** ses_01HXYZ...
**Created:** 7/24/2026, 3:00:00 PM
**Updated:** 7/24/2026, 3:12:00 PM

---

## User

The login button does nothing. Here's the logs.

---

## Assistant

I'll investigate the login handler.

_Thinking:_

The button onClick is wired in auth.ts...

**Tool: read**

**Input:**
```json
{ "path": "src/auth.ts" }
```

src/auth.ts (200 lines)

---

## Assistant

Found it — the handler returns early.
```

Header block is `# {session.title}` then four `**Label:** value` lines (id, created, updated) then a `---` rule (`packages/tui/src/routes/session/index.tsx:3056`). Messages are joined with `\n\n---\n\n`.

**JSON formats (two variants, both TUI-only):**
- Plain JSON: `{ info: Session.Info, messages: SessionMessage.Info[] }`, built by cursor-paginating `client.api.message.list({sessionID, limit:200, order:"asc"})` to exhaustion (`packages/tui/src/routes/session/index.tsx:767-778`).
- Debug JSON: `{ info: Session.Info, events: SessionEvent[] }`, built from `client.api.session.log({follow:false})` merged with in-memory connection history, ordered by `event.created` (`packages/tui/src/routes/session/index.tsx:750-764`).

**Authoritative types:**
- `Session.Info` — `packages/schema/src/session.ts:24-46` (id, parentID, fork, projectID, agent, model, cost, tokens, time{created,updated,archived}, title, location, subpath, revert).
- `SessionMessage.Info` — tagged union on `type`, 9 members (`packages/schema/src/session-message.ts:243-256`): `agent-switched`, `model-switched`, `user`, `synthetic`, `system`, `skill`, `shell`, `assistant`, `compaction`.
- `SessionMessage.Assistant.content` — tagged union on `type`: `text` | `reasoning` | `tool` (`packages/schema/src/session-message.ts:174-177`).

## v2 data model

**Single SQLite DB**, same XDG location as v1: `$XDG_DATA_HOME/opencode/opencode.db` (or `opencode-<channel>.db` for non-prod channels). Configured at `packages/core/src/database/database.ts:42-56`, WAL mode (`packages/core/src/database/database.ts:30-35`). Full DDL in `packages/core/src/database/schema.gen.ts`; drizzle defs in `packages/core/src/session/sql.ts`.

**Architecture: event-sourced with projections.** Durable events land in the `event` table and are folded by `SessionProjector` (`packages/core/src/session/projector.ts:461` onwards) into read-model tables.

**Relevant tables** (with `file:line` in `packages/core/src/database/schema.gen.ts` / drizzle in `packages/core/src/session/sql.ts`):

| v2 table | Purpose | schema.gen | sql.ts |
|---|---|---|---|
| `event` | durable event log: `id, aggregate_id, seq, created, type, data` | `:79-89` | — |
| `event_sequence` | per-aggregate seq counter + owner | `:72-78` | — |
| `session` | session metadata projection (rich) | `:209-246` | `sql.ts:24-75` |
| `session_message` | **canonical v2 message store** | `:185-196` | `sql.ts:109-128` |
| `message` | legacy v1-shaped message rows | `:164-173` | `sql.ts:77-89` |
| `part` | legacy v1-shaped part rows | `:174-184` | `sql.ts:91-107` |
| `session_pending` | durable prompt-admission inbox | `:197-208` | `sql.ts:130-153` |
| `instruction_entry` / `_blob` / `_state` | instruction sync state | `:136-163` | `sql.ts:155-184` |
| `session_share` | share URLs | `:247-257` | — |

**`session_message` is the table cotails must read for v2.** Columns: `id (msg_*), session_id, type, seq, time_created, time_updated, data`. `data` is the JSON-encoded `SessionMessage.Info` minus `id`/`type` (those are promoted to columns). Decoder pattern at `packages/core/src/session/store.ts:42-55` and `packages/core/src/session/history.ts:52-61`. Unique index on `(session_id, seq)` (`schema.gen.ts:269`).

**Map v1 → v2:**

| cotails v1 table | v2 equivalent | notes |
|---|---|---|
| `session` | `session` | v2 has ~20 extra columns (cost, tokens_*, fork_*, summary_*, time_compacting/archived/suspended, revert, permission, agent, model, share_url). v1 row shape mapped via `sessionRow()` in `packages/core/src/session/projector.ts:60-99`. `time_created`/`time_updated` column names are unchanged. |
| `message` | `session_message` (canonical) / `message` (legacy) | v2 `session_message.data` is a flat tagged union per row; v1 `message.data` was `{role, time, ...}` with a separate `part` join. |
| `part` | folded into `session_message.data.content[]` for assistant messages | v2 has no separate parts table for native sessions. `AssistantContent` = `text \| reasoning \| tool` (`packages/schema/src/session-message.ts:174-177`). |
| `event` | `event` | v2 `event` is keyed by `(aggregate_id, seq)` where aggregate_id = sessionID; v1 `event` was a session-scoped stream. Semantics differ — v2 events are the source of truth, projections are rebuildable. |

**The legacy `message`/`part` tables ARE still written** — but only by projector handlers for v1 events (`SessionV1.Event.MessageUpdated` at `projector.ts:516-529`, `PartUpdated` at `:566-584`, `MessageRemoved`/`PartRemoved` at `:530-565`). The v2 runner emits ONLY `SessionEvent.*` events (`packages/core/src/session/runner/publish-llm-event.ts`, `llm.ts`, `retry.ts` — 22 publish sites, all `SessionEvent.*`). The sole v1 event emitted by v2 core is `SessionV1.Event.Created` (`packages/core/src/session.ts:374`), used only to seed the `session` row.

➡ **Consequence:** a v2-native session will have a `session` row and `session_message` rows, but EMPTY `message`/`part` tables. cotails' current v1 reader will list the session but find no content.

## Ordering & ranges

**Stable ordinal = `session_message.seq`.**
- `seq` is assigned from `event.durable.seq` at insert time (`packages/core/src/session/projector.ts:443-458`, specifically `seq: event.durable.seq` at `:453`). `Event.Seq` is `Int >= 0` (`packages/schema/src/event.ts:20`).
- Per-session unique via `session_message_session_seq_idx` (`packages/core/src/database/schema.gen.ts:269`).
- Monotonic per aggregate; the `event_sequence` table (`schema.gen.ts:72-78`) hands out the next seq.
- **Caveat: gaps after revert.** Revert deletes `session_message` rows with `seq >= boundary.seq` (`packages/core/src/session/projector.ts:760-762`). So ordinals are stable and time-ordered, but NOT necessarily contiguous. Treat `seq` as a dense-as-possible monotonic rank, not `1..N`.

**Date ordering:**
- `session_message.time_created` (ms epoch) is indexed standalone (`session_message_time_created_idx`, `schema.gen.ts:277`) and compound as `(session_id, time_created, id)` (`schema.gen.ts:275`). Date-range queries on messages are cheap.
- `session.time_created` / `time_updated` on the session row for session-level date filtering. No standalone index on these beyond the PK; if cotails filters sessions by date it may want to scan or add an index.

**Existing range API (HTTP):** `session.messages({sessionID, limit, order: "asc"|"desc", cursor: {id, direction}})` (`packages/core/src/session.ts:472-505`). Anchors on `seq` (`session.ts:478-491`) and orders by `asc(SessionMessageTable.seq)` / `desc(...)` (`session.ts:500`). Cursor is base64url-encoded `{id, order, direction}` (`packages/server/src/handlers/message.ts:10-25`). Default limit 50 (`packages/server/src/handlers/message.ts:8`). This is the ready-made mechanism for "messages from ordinal N onward" (walk with `order=asc` from a cursor) but there is no direct "ordinals N..M" slice API.

**Recommendation for cotails ranges:**
- By ordinal: read `session_message WHERE session_id=? ORDER BY seq ASC`, then apply 1-based ordinal offsets in cotails. Account for revert gaps (rank by position in result set, not by raw `seq` value, if contiguous ordinals are desired).
- By date: `WHERE session_id=? AND time_created >= ? AND time_created < ? ORDER BY seq ASC` (seq order ≈ chronological order within a session; the compound index covers it).

## Impact on cotails

1. **cotails will silently miss v2 content.** Reading v1 `message`/`part` returns nothing for v2-native sessions even though the `session` row exists. This is the single biggest breakage.
2. **Add a `session_message` reader.** The `data` JSON is a flat tagged union per row — no `part` join needed. Decoder shape is `SessionMessage.Info` (`packages/schema/src/session-message.ts:243-256`). cotails can mirror the decode logic at `packages/core/src/session/history.ts:52-61` (`{...row.data, id: row.id, type: row.type}`).
3. **DB location is unchanged.** cotails keeps its single-DB reading model; just point the new reader at the same SQLite file and add a `session_message` query.
4. **Search targets change shape.** v1 searched across `part` rows (text/reasoning/tool). v2 searchable text lives in: `session_message.data` JSON for `user.text`, `assistant.content[].text`/`reasoning.text`, `assistant.content[].name`/`state.input`/`state.content[]`, `shell.command`/`output`, `system.text`, `synthetic.text`, `skill.text`. SQLite `json_extract` on `session_message.data` is the v2-native way (the projector already uses this pattern, e.g. `packages/core/src/session/projector.ts:246`, `packages/core/src/session/history.ts:23`). Regex-over-JSON-text (cotails' current approach) still works as a fallback.
5. **Roles vocabulary expands.** v1 had `user`/`assistant`/`system`. v2 message `type` adds `agent-switched`, `model-switched`, `synthetic`, `skill`, `shell`, `compaction`. Decide which to show in search results and in dumps (v2's own renderer skips everything except user/shell/assistant — see `formatSessionTranscript`).
6. **`seq` vs `time_created` for ordering.** Prefer `seq` within a session (matches v2's own reads); `time_created` for cross-session/date filtering.
7. **No event-table migration.** cotails' v1 `event` reader is not portable — v2 `event` rows are the durable source-of-truth log (different schema, different semantics). For cotails' purposes, `session_message` is the right read model and the `event` table can be ignored.

## Recommendations for the session-dump ticket

1. **Reuse `formatSessionTranscript`'s markdown shape verbatim** (`packages/tui/src/routes/session/index.tsx:3034-3057`) so cotails' output is byte-compatible with what the v2 TUI "Export session transcript" produces. Header block, `## User` / `## Shell` / `## Assistant` sections, same tool/input/output formatting, same `\n\n---\n\n` joins. This makes cotails a drop-in CLI for what v2 only offers behind a TUI dialog.
2. **Offer both markdown and JSON outputs**, matching v2's two JSON variants: `{info, messages}` (paginated `SessionMessage.Info[]`) and optionally `{info, events}` debug mode. cotails' CLI advantage is `--format md|json|json-debug` with stdout output, which v2 lacks.
3. **Implement ordinal ranges first** (`--from N --to M` or `--range N:M`) using `session_message.seq ORDER BY seq ASC`, with 1-based positional ranking over the result set (to hide revert gaps). Date ranges (`--since`/`--until`) are a straightforward second mode on the same query.
4. **Add a `--sanitize` flag** mirroring v1's `opencode export --sanitize` (`packages/opencode/src/cli/cmd/export.ts:231-234`, redaction helpers at `:11-33`). cotails is a natural place to carry this forward since v2 dropped it from the CLI surface.
5. **Read from `session_message` for v2, fall back to `message`/`part` for v1.** Auto-detect per session (e.g. "does this session_id have any `session_message` rows?"). This lets cotails dump both v1-created and v2-created sessions from the same DB during the transition.
6. **Do NOT duplicate the dump behind a TUI.** cotails' value is exactly that it is a non-interactive CLI — fill the gap v2 left open. Confirm with the v2 team before diverging from `formatSessionTranscript` formatting.
